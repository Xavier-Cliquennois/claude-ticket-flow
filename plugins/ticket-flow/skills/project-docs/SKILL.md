# project-docs

Docs are written in the language the repo's docs already use; for a new repo, in
the user's language. Code identifiers stay as they are.
Everything renders on GitHub as-is: plain Markdown, Mermaid in fenced blocks, SVG
files. No doc site generator unless the project already has one.

## The layout

```
README.md            what it is, how to start, link to docs/README.md
CLAUDE.md            how to work in the repo (agents and humans)
CHANGELOG.md         what changed, per release (optional)
docs/
  README.md          the index: one line per doc, what it answers
  architecture/      how the system is built (overview first)
  guides/            how to do X: install, deploy, test, operate
  reference/         lookup material: API routes, data model, config, formats
  decisions/         ADRs, NNNN-titre-court.md, never edited after acceptance
  brainstorms/       dated session notes from the brainstorm skill, out of the index
  assets/            svg, png, pdf referenced by the docs
  archive/           superseded docs, kept for history, out of the index
```

A project with a strong existing taxonomy (e.g. `docs/protocole-*.md`) keeps it:
apply the rules below inside it rather than moving everything.

What is NOT documentation and does not belong in `docs/` (nor at the root):
plans, roadmaps and TODO lists (→ tickets), prompts written for a model, audits
and one-off reports (→ the ticket that asked for them, or `archive/`), backups
(`*_BACKUP_*`, → delete, git has the history), generated outputs.

## Rules for every doc

- **Name**: `kebab-case.md`, lowercase, no spaces, no accents in file names.
- **Opening**: an H1, then one sentence saying what question this doc answers,
  then `> À jour au <AAAA-MM-JJ> (<commit court>).`
- **Describes what IS.** History goes to CHANGELOG, tickets and ADRs. A paragraph
  starting "Avant, on faisait..." is a sign the doc needs a rewrite, not an addendum.
- **One subject, one place.** Link instead of copying. Past ~400 lines, split.
- **Paths and names are checkable**: every file, function, command, env var
  written in backticks must exist. That is what the audit verifies.
- **Same commit as the code.** A change that makes a doc wrong updates it in the
  same commit/PR. A ticket's "Fini quand" carries the box
  `- [ ] doc à jour (ou : aucune doc concernée)`.
- No secrets, tokens, real customer data or internal URLs with credentials, even
  in examples.

## Diagrams

Choose by what the picture shows:

| Shows | Use |
|---|---|
| a flow, a pipeline, who calls what | Mermaid `flowchart` |
| an exchange over time (request, webhook, auth) | Mermaid `sequenceDiagram` |
| a data model | Mermaid `erDiagram` |
| a lifecycle (ticket, order, status) | Mermaid `stateDiagram-v2` |
| a planning | Mermaid `gantt` |
| space, geometry, layout, a physical setup, a UI sketch | hand-written SVG in `docs/assets/` |
| a screenshot of the real UI | PNG in `docs/assets/`, dated in its caption |

Mermaid:
- Inside the doc in a ```` ```mermaid ```` block, so it diffs with the text.
- Short node ids, labels in quotes when they contain punctuation:
  `A["Route API /api/x"]`. Max ~15 nodes per diagram: split beyond that.
- No custom colors/themes (GitHub light and dark both render the default).
- Validate before committing:
  `npx -y @mermaid-js/mermaid-cli -i <doc.md> -o /tmp/mmd-check.md` (fails on a
  syntax error; delete the output).

SVG:
- Written by hand or generated by a script kept next to it (`docs/assets/x.py`
  → `x.svg`), never an export with embedded fonts or base64 rasters.
- `viewBox` set, no fixed `width`/`height` (or width="100%"), units in the
  drawing's real scale when it is to scale (say the scale in the caption).
- Readable in GitHub light AND dark: give the drawing its own background
  (`<rect width="100%" height="100%" fill="#fff"/>`) or use an inline
  `<style>` with `@media (prefers-color-scheme: dark)`. Never rely on the page
  background.
- `font-family="system-ui, sans-serif"`, text ≥ 12 px at the viewBox scale,
  a `<title>` element for accessibility.
- Embedded with alt text and a caption: `![Placement des caméras](assets/camera-placement.svg)`
  then a line in italics saying what to look at.
- Check it renders: open it in the browser (Chrome tools, or Playwright if Chrome
  is closed) or `qlmanage -t -s 800 -o /tmp file.svg` on macOS, and look at it.

## Audit mode ("audite / range la doc")

Read-only first, then propose; move or delete nothing without the user's yes.

1. Inventory: every `*.md`, `*.svg`, `*.pdf`, `*.html` at the root and under
   `docs/` (skip `node_modules`, `.venv`, `.next`, worktrees), with size and last
   commit date (`git log -1 --format=%cs -- <file>`).
2. For each doc:
   - **broken references**: backticked paths that don't exist
     (`test -e`), relative links and images that don't resolve;
   - **stale**: last touched long before the code it describes
     (compare with `git log -1` of the files it names);
   - **orphan**: not linked from `docs/README.md` nor from any other doc;
   - **misplaced**: plan/prompt/audit/backup, root clutter, wrong naming;
   - **duplicates**: two docs answering the same question.
3. Report as a table: doc, problem, proposed action
   (garder / mettre à jour / déplacer vers X / archiver / supprimer / fusionner avec Y).
4. On approval: `git mv` (keeps history), fix every inbound link
   (`grep -rn "<ancien-nom>"`), write or update `docs/README.md`, one commit
   per kind of change (`docs: range ...`, `docs: met à jour ...`).

Updating stale content is real work: each substantial rewrite is its own ticket
(`write-ticket`, type `doc`), not a side effect of the cleanup commit.
